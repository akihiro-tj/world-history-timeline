# E2E テスト導入 設計

Gherkin 記法（`.feature`）で書いたシナリオを playwright-bdd で実行し、実ブラウザでの動作を検証する。既存の jsdom + React Testing Library によるテストは維持し、E2E は実ブラウザでの通しの動作確認を担う。

## 背景と課題

- 実ブラウザでの検証手段がない。テストは 175 件あるが、すべて jsdom 上で動く。実際のページリロード・実ビューポートの CSS メディアクエリ・実ブラウザの SVG 描画は検証できていない
- 初期描画時のちらつき対策（`index.html` の同期スクリプト）が機能しているかを確認する手段がない。この処理は React のマウント前に走るため、jsdom のテストでは到達しない
- テーマとオンボーディングの永続化テストは unmount + render で代替しており、実際の `location.reload()` を経ていない。localStorage と初期化スクリプトの連携は実ブラウザでしか確かめられない

## 手法の選定

Gherkin 記法 + playwright-bdd を採用する。

Playwright に公式の BDD サポートはないため、Gherkin を使うなら外部ライブラリに乗ることになる。playwright-bdd は `.feature` を Playwright のネイティブテストへ変換する形を取り、Playwright ランナーの機能（自動待機、trace、並列実行、fixtures）をそのまま使える。保守は継続的に行われている。

`.feature` ファイルがシナリオの単一の情報源になる。仕様と実行されるテストが同じ成果物なので、仕様だけが古くなる状態を避けられる。

### 採用しなかった案

- **素の `@playwright/test`** — 依存が公式のみで最も単純。シナリオが少数なら Gherkin の抽象化は割に合わないが、今回は 14 シナリオを書くため、自然言語で意図を表現できる利点を取った
- **markdown の表を実行時にパースする独自 DSL** — 表形式で一覧性が高い一方、パーサとディスパッチャを自前で保守することになる。既製のライブラリで足りる範囲に自作の仕組みを持ち込まない

## 検証範囲

E2E は主要機能を網羅する。jsdom で再現できない領域に加えて、ユーザーが実際にたどる操作の流れを実ブラウザで確認する。

RTL のテストと一部重複するが、これは意図した重複とする。RTL は個々の振る舞いを細かく速く検証し、E2E は実ブラウザで通しで動くことを検証する。同じ仕様変更で両方を直す場面は生じる。

### シナリオ一覧（14 本）

jsdom で検証できない領域:

1. テーマをダークにしてリロードしても維持される
2. OS がダーク設定なら初回描画から暗い（ブラウザのカラースキームをダークにしてページを開き、最初の描画の時点でダークが適用されていることを確認する。描画フレーム単位でのちらつきの有無までは検証しない）
3. オンボーディングを閉じてリロードすると再表示されない
4. デスクトップで詳細パネルが右に表示される
5. モバイルで詳細パネルが画面下半分に表示される
6. 年表の SVG が描画されスクロールできる

主要な操作の流れ:

7. 検索で人名を入力して選ぶと、その時代へ移動し解説が表示される
8. エントリをクリックすると解説と同時代の出来事が表示される
9. 拡大すると、より詳しい人物・事件が現れる
10. 年号（前300 など）を入力してジャンプする
11. 同時代リンクをクリックすると選択が移る
12. 全体表示ボタンで俯瞰に戻る
13. ドラッグでパンできる
14. ズームすると国名の2段目ヘッダーが現れる

## 構成

```
tests/
  e2e/
    features/          .feature ファイル（シナリオ）
    steps/             ステップ定義
playwright.config.ts
```

`.feature` は機能単位で分ける（テーマ切り替え、オンボーディング、検索、エントリの選択、ズーム、レイアウト）。ステップ定義は再利用しやすい粒度で書き、シナリオ固有の複雑な操作をステップの中に隠さない。

`playwright.config.ts` は desktop と mobile の 2 プロジェクトを持ち、ビューポート依存のシナリオはタグで振り分ける。失敗時に trace を保存する。

配信するサーバーは環境で切り替える。ローカルでは起動が速い開発サーバーを使い、既存のサーバーがあれば再利用する。CI ではビルド済みの成果物を配信し、本番と同じ出力を検証する。

## CI

`check` ジョブの後段に E2E を組み込み、すべての PR で 14 シナリオを実行する。シナリオ数が少ないうちは smoke と full を分ける利点がないため、分割はしない。実行にはブラウザのインストールが必要になるため、その分の時間は増える。

E2E はビルド済みの成果物に対して実行する。`check` ジョブが既に dist をアーティファクトとして保存しているので、これを使えば開発サーバーではなく本番と同じビルドを検証できる。

## テスト方針

- シナリオは日本語で書く。UI 文言が日本語であり、シナリオもそれに合わせる方が読みやすい
- ステップ定義ではロールとアクセシブル名でロケータを組み立てる。CSS セレクタや実装の内部構造に依存しない
- 実データ（`public/data/*.json`）に対して実行する。E2E 用のモックデータは持たない。テストが特定のエントリに依存する場合は、教科書レベルの基本的なエントリ（データの整理で消えにくいもの）を選ぶ
- 既存の jsdom + RTL のテストは変更しない

## 検討した代替案

- **E2E を jsdom で不可能な範囲だけに絞る（6 シナリオ）** — 維持コストは最小になるが、ユーザーがたどる操作の連続性が実ブラウザで確認されない
- **PR では smoke のみ、main で全件** — PR のフィードバックが速くなるが、タグの管理が増える。シナリオが増えたら再検討する
- **デスクトップのみで実行** — 実行時間は短いが、パネルの配置が画面幅で切り替わる実装のため、モバイルのレイアウトを検証できない
- **複数ブラウザ（WebKit / Firefox）での実行** — クロスブラウザの問題を拾えるが、個人プロジェクトでは実行時間に対する効果が薄い
